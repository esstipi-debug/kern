## What Kern is

> Renamed from **Linchpin** on 2026-07-12 — narrative in

> (2026-08-19, together with the Odoo 19 port).

An **agentic supply-chain engine**: a plain-language brief becomes a finished,
QA-gated deliverable (Excel + report + chart), grounded in a knowledge graph of
27 curated external sources and the codebase itself. A deterministic Python **engine** across
**60 agent-routable tools** (EOQ, safety stock, `(s,Q)`/`(R,S)`, simulation,
a network digital twin, forecasting, pricing, price intelligence,
discovery-assisted price watch, DDMRP, ABC-XYZ, sourcing, supplier segmentation (Kraljic),
landed cost, import case / document pack, cost-to-serve, S&OP, facility location, multi-facility network design (p-median),
DRP, transportation, FEFO, launch readiness, vehicle routing, hat tension/settlement,
flow map, cross-area impact/objection verdict, intake scan, realized customer
service, ISO operations floor evidence, MUS audit-evidence workpaper, SCOR/ISO
evidence pack…) sits under an
**orchestrator agent** that classifies → runs → validates → delivers. Runs
with or without an LLM.

Positioning: **the human sells & decides, Kern produces 10×.** Every
consequential result ends in one of four outcomes — and three need a human
(see *Never-unprotected* below).

## How the agent works

`brief → intent.classify → registry.get(tool) → prepare → run → QA → deliver → JobResult`

- **"QA fails ⇒ no deliverable"** is enforced in one place (the orchestrator).
- Statuses: `ok` · `needs_clarification` · `needs_data` · `qa_failed` · `error`.
- Adding a capability needs **no routing edits** -- the orchestrator never
  special-cases a tool. It is not one `register()` call, though: a new tool
  touches eight fixed places, listed in
  [`.specify/memory/constitution.md`](.specify/memory/constitution.md) so nobody
  has to re-derive them from git again.

### Never-unprotected (`nosilo_core.guided`)
Every consequential result is a `GuidedOutcome` with status:
`EXECUTED` (agent did it) · `OPTIONS` (ranked choices) · `HANDOFF` (prepared
human step) · `ESCALATED` (routed to a human with SLA). The last three need a
human — that contract is what `documentation/operator/` documents.

`cross_impact` mide el impacto de una decision propuesta sobre las otras areas
y emite un veredicto de objecion contra umbrales del perfil de cliente. Un
area sin umbral sale `no_evaluable` y el veredicto global es `indeterminado`
- nunca "nadie objeta".

### Los sombreros son CINCO, y el quinto es condicional (`src/hats.py`)
`HAT_KEYS` = comprador · planner · cfo · comercial · **transporte**. El quinto
puntua el flete que la politica obliga (`src/logistics/modes.py`: el FTL cobra
por `ceil(peso/capacidad)`, asi que la curva es un SERRUCHO en Q, no una
pendiente — el Q que alcanza un price break puede desbordar a un segundo camion
medio vacio). Necesita dos hechos fisicos que ninguna serie de demanda trae:
peso por unidad (columna `weight_kg` del CSV) y largo de la ruta (param
`distance_km`). Sin ambos, `evaluable_hats(inputs)` lo deja FUERA — no se
inventa un kilogramo — y toda superficie que renderice un consejo tiene que
NOMBRAR la exclusion: cuatro sombreros de acuerdo en silencio se lee igual que
cinco de acuerdo, y solo una de las dos cosas es cierta. En `cross_impact` esa
exclusion cuenta como `no_evaluable`, o sea `indeterminado`: **una corrida sin
datos de flete ya no puede devolver "ejecutar"**. `decision_cost` suma flete
solo cuando hay perfil declarado (sumar cero diria que la politica despacha
gratis, y ademas mantiene intacta la equivalencia con
`jobs/inventory_optimization.py` que fija `tests/test_hats_valuation.py`).

### Writeback safety (`nosilo_core.writeback`)
Never mutate a system of record blindly: stage a dry-run `Changeset`, classify by
risk tier (`read`/`reversible`/`irreversible`), gate on a time-boxed `Approval`
(900 s TTL), apply idempotently, `rollback()`-able. Irreversible always needs
explicit approval. Real connectors implementing the store surface: Odoo
(`src/connectors/odoo.py`) and client Excel workbooks (`src/connectors/excel.py`
— drift check vs the live file, atomic temp+replace write, per-commit file
backup, cell-exact rollback; `.xlsm` macros preserved via `keep_vba`, never
executed).

### Service coverage (`src/connectors/__init__.py`, read side)
The mirror of writeback safety, on the way in. `src/order_fulfillment.py` measures
fill rate, outbound OTIF (SCOR RL.1.1) and lost sales from three OPTIONAL fields on
`OrderLine`; which of the three a backend can fill is the competitive question the
AU/NZ channel work rests on. So **every module in `src/connectors/` that defines
`orders()` or `arrivals()` must export a `SERVICE_COVERAGE`** declaring, field by
field, `status` (measured / derived / unavailable), `source` (the vendor's own field
name) and `means` (what the number IS, in a sentence).
`tests/test_connector_service_contract.py` does not read it — it **runs** it against
the adapter and fails in both directions, and a new module without one breaks the
build.

The client's own file is the other producer: `jobs.intake.service_lines(path)` returns
the `order_lines` frame when the export carries any of the three (aliases in en/es/pt),
and `inventory_optimization` forwards it — so a plain CSV run reports measured service
without any connector. That frame's `.attrs["service_note"]` carries the caveat a
vendor doc makes unnecessary: from a file you cannot know whether `fecha_entrega` is a
dispatch or an arrival, so the summary names the matched column and says so.

The `means` sentence is the load-bearing part, not decoration: Unleashed, Cin7 Core
and Odoo all fill `delivered_date` with a **departure**, Olist and Shopify with an
**arrival**. Same field, same type, opposite meaning. Measured on 98.666 real orders
(`examples/run_service_report.py`), the gap is 6.2 points of OTIF — the last leg no
ERP in the channel can see. `arrivals.ArrivalSource` is the separate Protocol for
carriers (Starshipit), which know when a shipment landed and nothing else: an ERP and
a carrier together can measure arrival OTIF, and neither can alone.

### Discovery-assisted price watch (`jobs/price_watch.py`, read-only)
Auto-onboard a never-seen competitor site, homologate its product pages against
your catalog, then re-acquire and monitor the confirmed pairs on a recurring
cadence. Two hard invariants: it is **100% read-only observation** — no price is
ever written back to any competitor, marketplace, or your own catalog anywhere
in the pipeline (`nosilo_core.writeback` is never imported); and **auto-onboarding is
robots.txt-only and always `limited`** (`tos_decision` is never `"allowed"`,
`max_tier_allowed` never above `L1` — robots.txt says nothing about a site's
ToS, so no automated basis to claim a human legal review). A tier raise beyond
the approved ceiling is surfaced as a pending-approval `GuidedOutcome` (R5),
never applied alone. End-to-end CLI: `examples/run_price_watch.py`
(`--url <competitor_url> --catalog <our_catalog.csv>`, or `--demo`); acceptance
proof in `tests/test_price_watch_e2e.py`.

### Terminos del proveedor: dos terminales, nunca un punto muerto (`src/constraints.py`)
Kern dice 40 y el proveedor vende de a 30, 60, 90. `apply_order_rules` sigue
siendo el redondeo de una sola terminal (arriba); lo que decide es
`cheapest_feasible_lot`: valua los dos lotes legales vecinos con la misma curva
de costo del EOQ (`src.eoq.total_cost`), elige el mas barato y devuelve el otro
como `alternative` con su penalidad. Cuatro consumidores leen la MISMA regla
(`lot_rule`/`is_feasible_lot`) y por eso nunca discrepan sobre que es "factible":
- **`jobs/inventory_optimization.py`** lee `moq` / `order_multiple` (intake los
  emite SOLO cuando el archivo los trae; alias en es/en) y en `(s,Q)` mueve Q,
  ciclo, inversion y beta implicita al lote elegido; el registro lleva
  `order_quantity_unconstrained`, `lot_rule`, `lot_penalty_usd` y
  `lot_alternative_qty`. `jobs/qa.py` rechaza una Q que el proveedor no acepta o
  una alternativa mas barata que la elegida. `tool_options.inventory_options`
  agrega la OPCION "Renegotiate supplier terms" con la lista por penalidad; un
  `(R,S)` con terminos sale como residual (la regla se lleva, no se aplica).
- **`src/hats.py`**: con terminos la grilla son lotes legales (`candidate_grid`,
  piso `MIN_FEASIBLE_Q_POINTS` en vez de 125 candidatos) y `baseline_plan` es el
  mismo lote que despacha el job. `verify_tension`/`verify_settlement` rechazan
  un ideal o un acuerdo infactible.
- **`jobs/cross_impact_job.py`**: una propuesta infactible se mide igual, pero
  sale un residual que nombra los lotes legales vecinos.
- **El camino Odoo** (`src/connectors/replenish.py`, `src/connectors/odoo.py`):
  `purchasable_quantity` lleva lo que se ESCRIBE hacia arriba al paso de la unidad
  del producto (`OdooConnector.unit_step_by_sku`) y, en la OC, al `min_qty` del
  proveedor. Una pieza (categoria "Unit") tiene paso 1 aunque "Units" venga de
  fabrica con `rounding=0.01` -- redondear a esa precision dejaba 187,6 rollos en la
  OC --; el resto va a su `rounding`. El plan redondea (CSV, OC y punto de reorden
  dicen el mismo numero) y conserva la cifra en `restock_unrounded`. Un producto que
  se compra en otra unidad (`uom_po_id`: docena, caja) va a la OC ENTERO en esa
  unidad -- cantidad, unidad y precio --, porque ahi estan el `min_qty` y el precio
  del proveedor; la linea nombra la unidad (`product_uom`, o `product_uom_id` en
  Odoo 19).
Lo que NO se hace: leer `product.packaging` de Odoo (`src/connectors/odoo.py`
lee `min_qty` y las unidades del producto) -- trabajo de conector, sin instancia
viva con cajas cargadas para probarlo.

### El tool CSV ve el estante y lo que viene en camino (`jobs.intake.stock_position`)
`inventory_optimization` dimensiona `s` y `Q` (cuanto); la posicion dice CUANDO.
Si el archivo trae stock en estante (`on_hand`: stock, existencia, saldo...) y,
opcional, stock en camino (`on_order`: en_transito, por_recibir, oc_pendiente,
open_po...), `stock_position(path)` toma la ULTIMA fila por SKU y el job agrega
`inventory_position = net_flow_position(on_hand, on_order, 0)` (la identidad de
`src/ddmrp.py`, no una segunda formula), `order_now` y `order_qty_now` por SKU;
`tool_options` suma la OPCION "Release the N orders due now". Dos reglas de
`tests/test_neteo_en_transito.py` valen aca igual: el en-transito netea el
DISPARADOR, no solo la cantidad (una OC atrasada por transporte no se vuelve a
pedir: `n_reorders_avoided_by_transit`), y la ausencia se declara -- sin columna
de en-transito `on_order` es `None`, nunca 0, y deck, md, options y resumen
dicen que NO se pudo netear. Las dos columnas NO entran en `CANONICAL_OPTIONAL`:
un stock es una foto y `normalize_tracked` agrega flujos por periodo.

### Nadie compra dos veces lo que ya viene en camino
El neteo contra la posicion (`NFP = on_hand + on_order`, `src/ddmrp.py`) vive en UN
lugar y ya lo leen los cinco emisores de cantidad a pedir: la planilla
(`excel_replenishment`), el ERP (`odoo_replenishment`), `ddmrp`, el tool CSV
(arriba) y, desde C, los tres que faltaban:
- **`shopify_replenishment`**: `ShopifyConnector.incoming_by_sku()` lee la cantidad
  `incoming` de Shopify (transferencias entrantes y OC del propio admin) en la MISMA
  consulta que ya pedia `available` -- una llamada por item, no dos.
- **`channel_replenishment`**: reusa literal `jobs.odoo_job.read_on_order`; un ERP que
  no expone OC abiertas (Unleashed hoy) se declara por su nombre.
- **`drp`**: `Branch.scheduled_receipts` por (sucursal, periodo) entra al grid ANTES
  del requerimiento neto, como manda el DRP de manual; el CD las recibe por params.
La regla que comparten: **la ausencia se declara**. Sin dato, `on_order` es `None` --
nunca 0 -- y el CSV deja la celda en blanco, el deck pone un finding "do NOT net" y
las OPTIONS un residual. Un cero significaria "medido, y no viene nada", que manda al
comprador a no restar nada. Y el neteo alcanza al DISPARADOR, no solo a la cantidad.

Que esos ocho neteen NO es una creencia: lo mide `src/bateria/barrido_neteo.py`,
corriendo cada emisor DOS veces (con y sin en-transito) y exigiendo que la cantidad
baje. Sondea los **catorce** tools del registro que ponen un numero de compra en manos
del operador, y los otros 46 tienen que declarar por escrito por que no lo hacen:
`tests/test_barrido_neteo.py` recorre `build_default_registry()` y se pone rojo si un
tool no esta clasificado. Nacio porque la bateria puntua el MEJOR candidato de T05 y
por eso estuvo en verde los meses en que el tool central no miraba el estante -- un
tool que nadie sondea no se puede poner rojo. T05 ahora CONSUME esas sondas, asi que
"netea" se define una sola vez. Estado publicado y congelado en
[`documentation/KERN_BARRIDO_NETEO.md`](documentation/KERN_BARRIDO_NETEO.md): **8 netean**,
6 no tienen canal (`newsvendor`, `sop`, `multi_echelon`, `simulation`, `hat_tension`,
`hat_settlement`) y ninguno tiene el dato sin usarlo.

`launch_readiness` fue el octavo, el 2026-09-18, y netea DISTINTO: contra una FECHA. Su
veredicto preguntaba si el estante alcanza para llegar al lanzamiento, asi que salia
ROJO -- "una orden no puede llegar a tiempo" -- sobre stock que ya estaba comprado y en
camino. Ahora el archivo puede traer `on_order` y su **ETA**, y el en-transito cuenta
**solo si aterriza en o antes de la fecha de lanzamiento**; con ETA posterior no cuenta
y lo dice, y con cantidad pero SIN ETA tampoco cuenta -- contarla seria inventar una
fecha -- pero el veredicto la NOMBRA y explica que columna agregar. Por eso su sonda
corre tres veces y no dos: acredita solo si lo que llega a tiempo mueve el veredicto Y
lo que llega tarde no lo mueve.

### Una negativa del motor no puede salir vestida de numero (`jobs/inventory_optimization.py`)
`inventory_optimization` se NIEGA a dimensionar un SKU con menos de
`MIN_PERIODS_FOR_POLICY` (6) periodos o sin costo usable -- correcto, y el codigo lo
dice: *"Refuse rather than degrade"*. Hasta el 2026-09-19 emitia esa negativa con
`forecast`, `reorder_point`, `safety_stock` y `z_factor` en **0.0**, `status="ok"`,
`qa_issues=[]` y un resumen que decia *"recommended inventory investment $0"*. El
aviso existia pero viajaba por la prosa (`policy_kind`, `method="none"`, un residual
de `tool_options`); el NUMERO decia lo contrario, y todo consumidor lee el numero:
- `src/simworld/runners.py` lo ejecutaba como "no pedir nunca";
- `jobs/state_bridge.py::_usable` existe justamente para omitir esa linea -- *"un
  disparador ausente no es cero (pediria siempre) y una demanda diaria ausente no es
  cero"* -- y el `0.0` del productor la DERROTABA, asi que `src/alerting.py` emitia
  **`dead_stock`** ("N units on hand with no demand") sobre un SKU que vendia ~42
  u/semana con 120 en el estante. Reproducido punta a punta en
  `tests/test_negativa_no_es_cero.py`.

Los cuatro campos son `float | None` y la ausencia va en `None`. **`skipped_zero_demand`
CONSERVA sus ceros**, y esa es la otra mitad de la regla: ahi la demanda SI se midio y
dio cero, asi que el 0 es una medicion -- y por eso el `dead_stock` legitimo sigue
saliendo. `jobs/qa.py::_sized_field_issues` gatea las DOS direcciones (una linea sin
politica no puede traer un numero; una con politica no puede traer un `None`), porque
anular todo seria el mismo defecto al reves. `src/verify/coherencia.py::POLITICAS_SALTADAS`
quedo alineada con `jobs.qa.UNPRICED_POLICY_KINDS`: tenia dos de las tres clases, asi
que `insufficient_history` entraba al analisis con sus ceros y pasaba toda invariante
trivialmente.

La cantidad que el marcador emite **no cambia** -- captura identica al ultimo digito
sobre las semillas 1003/1004 --, porque `apply_policy` ya trataba un SKU ausente igual
que uno con disparador 0. Lo que cambia es que ahora se puede distinguir "me negue" de
"decidi no reponer".

**Y negarse a dimensionar no obliga a no decir nada** (2026-09-20). Son DOS preguntas y
hasta esa fecha se contestaban las dos con silencio: *cuanto buffer* necesita sigma y
sin `MIN_PERIODS_FOR_POLICY` periodos no hay sigma honesta -- sigue sin contestarse --,
pero *cuanto hace falta para llegar a la proxima reposicion* necesita la media medida y
el plazo del proveedor, que el archivo ya trae. Entre `MIN_PERIODS_FOR_COVER` (2) y
`MIN_PERIODS_FOR_POLICY` (6) periodos el job emite una **cobertura provisional**:
`src/risk_period.py::provisional_cover` = `media x (plazo + revision)`, que es el `mu_x`
de la ecuacion 6.4 -- la identidad del propio motor -- con el termino de seguridad
OMITIDO, no puesto en cero. Debajo de dos periodos no hay ni media que citar y la
negativa se queda entera.

**No es una politica y el registro lo declara en la FORMA de sus campos**: disparador y
objetivo si (`reorder_point == order_up_to == cobertura`), `safety_stock`, `z_factor` y
`forecast` en `None`. Cubre la media, o sea que se espera que se quede corta cerca de la
mitad de las veces, y toda superficie que la muestre tiene que decir esas tres cosas
(que el numero existe, que no tiene buffer, y que su capital va APARTE: el titular sigue
siendo `requested_investment`, las coberturas suman en `provisional_investment`). Por
eso las listas son **dos** y no una: `UNSIZED_POLICY_KINDS` es "el motor no puso ningun
numero" y la lee `jobs/qa.py` (que exige los cuatro campos en `None`), mientras
`NOT_FULLY_SIZED_POLICY_KINDS` le agrega la cobertura y la leen
`src/verify/coherencia.py::POLITICAS_SALTADAS` -- sus invariantes por SKU presuponen
buffer y z -- y `scm_agent/package_specs.py`, porque una cobertura sin buffer en la
planilla de pedidos del cliente pisa su numero propio y ademas PARECE una politica.
Colapsarlas rompe en los dos sentidos.

La cobertura tambien dice **CUANDO**: `_order_now` la trata con la aritmetica de un
`(R,S)` -- porque eso es, un objetivo de reposicion sin lote -- asi que entra en
`order_now` / `n_order_now` y en la OPCION "Release the N orders due now", que la
NOMBRA aparte ("no safety stock behind it"). Sin esa mitad el arreglo quedaba
partido: el marcador ejecutaba la cobertura (asi se midieron los +19,4 puntos) y la
lista que lee el cliente no la nombraba, o sea que el numero publicado describia una
corrida que un cliente no podia reproducir. El Tower, en cambio, la deja pasar
**callado a proposito** (`forecast` en `None`): `order_now` es una lista que el
operador va a buscar, pero un `rop_breach` es un evento que se empuja, y sin buffer el
estante cae por debajo la mitad de las semanas -- una alarma que suena la mitad de las
semanas es ruido.

### El Tower sensa sobre datos reales (`jobs/state_bridge.py`)
`run_all_monitors` lee `stock`, `forecast` y `outcomes`, y hasta el 2026-09-18 el UNICO
escritor de `stock` era el puente del marcador (`examples/run_world_sim.py`): en
produccion el bucle de sensado corria sobre vacio (H1). Los **cinco** jobs que leen una
posicion (`inventory_optimization`, `odoo_replenishment`, `shopify_replenishment`,
`channel_replenishment`, `excel_replenishment`) ahora escriben el snapshot, y los tres de
conector escriben ademas la demanda REALIZADA como `outcomes`/`actual_qty` con la fecha
de cada pedido. El mapeo de cada job vive en UN lugar (`jobs/state_bridge.py`), nunca
copiado.

- **Identidad, la misma regla que `forecast_cycle.store_from_params`**: sin
  `params["state_client_id"]` no se escribe nada y NUNCA la particion compartida; un id
  invalido levanta `ClientIdError` en vez de degradar. Cada reporte gana `state_note`.
- **`avg_daily_demand` es por dia CALENDARIO** (`replenish.daily_demand_by_sku`), no el
  promedio de `demand_by_sku` — cuyo periodo es un dia-CON-PEDIDOS. Sobre un SKU
  intermitente el segundo sobre-estima la tasa varias veces, y es justo el numero con el
  que el Tower calcula dias de cobertura: dispararia quiebres falsos.
- **La planilla en modo punto-de-reorden no escribe**: sin columna de demanda no hay tasa
  diaria y derivarla del ROP seria inventarla. La nota lo dice.
- **El Tower tambien netea** (cerrado el 2026-09-18; antes era el limite declarado de
  D). El dominio `stock` gana `on_order` como columna OPCIONAL y anulable -- los cinco

### Y esa fecha de fin por SKU esta CONSTRUIDA (`src/horizon.py`)
[`documentation/KERN_FECHA_DE_FIN_POR_SKU.md`](documentation/KERN_FECHA_DE_FIN_POR_SKU.md).
La regla vive en `src/horizon.py::cap_policy`, la fecha entra por
`jobs/intake.py::sku_end_dates` (columna opcional `end_date`, alias en en/es/pt, ninguno
ambiguo), la aplica `jobs/inventory_optimization.py`, la gatea
`jobs/qa.py::_horizon_issues` y la nombran las tres superficies. Solo
`inventory_optimization` la lee; los otros trece emisores siguen sin horizonte.

**La pregunta de seguridad que las dos mediciones dejaron abierta -- que pasa con una
fecha EQUIVOCADA -- se contesta con una regla, no con un numero: el tope puede ENCOGER
una politica, nunca anularla.** Un tope de cero es "no compres nunca mas", o sea una
discontinuacion, y esa la decide una persona. Por eso `cap_policy` tiene SEIS verdictos y
tres se NIEGAN a topear (`expired` -- la fecha ya paso o es hoy --, `would_zero` y
`unusable`): la linea sale dimensionada como si no hubiera fecha, y las tres superficies
la NOMBRAN (fila del Excel con su `horizon_verdict`, hallazgo del deck, residual de las
OPCIONES). Callarlas seria el peor silencio: el cliente creeria que el tope la cubrio.

**La traduccion se declara, no se supone.** La regla medida topea "las dos mitades", y el
arnes que la midio ejecuta todo como (R,S), o sea que NO tiene lote. Un `(s,Q)` real trae
`order_up_to=None` y sus dos mitades son `s` y `Q`, asi que la misma regla se aplica a
TRES cantidades. Por eso `HorizonCap` llama a sus campos `trigger`/`target`: ponerles el
nombre de una de las dos formas escondio un defecto real mientras se escribia esto -- un
(s,Q) decidia el tope mirando solo el disparador y dejaba pasar una Q de 302 sobre un
restante de 204.

Tres reglas de ausencia, con test cada una: sin columna el mapa es `None` y nunca `{}`;
una celda vacia no entra y NO cuenta como defecto (la mayoria de una cartera real no trae
fecha); una celda ILEGIBLE se descarta y se CUENTA, nunca se reemplaza por hoy. Y el
`as_of` es el fin del HISTORICO y no el reloj: un archivo que termina hace tres meses
sacaria todo el catalogo como `expired`. Un `*_before_horizon` aparece si y solo si ese
numero se movio -- en blanco, nunca en cero.

**Un archivo sin la columna sale IDENTICO a antes de la capacidad**
(`test_sin_fechas_el_job_sale_IDENTICO_a_antes_de_la_capacidad`), que es lo que la vuelve
segura sobre la base instalada.

### Y la fraccion de una cartera REAL que trae esa fecha esta medida
[`documentation/KERN_FRACCION_CON_FECHA_DE_FIN.md`](documentation/KERN_FRACCION_CON_FECHA_DE_FIN.md)
(`scripts/fraccion_con_fecha_de_fin.py`, sobre Olist: 32.729 SKU, 3.053 vendedores, 105
semanas; `scripts/fetch_olist.py` lo baja de un mirror publico sin credenciales).
**Ningun export real trae la columna**, asi que medir "cuantos archivos la traen" da cero
y no dice nada; lo medible es que fraccion de los SKU tiene un fin de vida, y si el
cliente lo SABIA de antemano NO se puede medir de un archivo de transacciones -- se
declara.

**13,8%-26,1% de los SKU y 8,9%-21,6% de la facturacion**, con tres correcciones que
cambian como se lee el techo de +13,1 puntos:
- **Pesar por plata da siempre MENOS que contar SKU** (en las cuatro carteras): los que
  mueren son los chicos, y el valor de la palanca escala con capital.
- **El nucleo muere la MITAD que la cola** (13,8% contra 26,1%), o sea que el techo --
  medido donde TODOS los SKU mueren la misma semana -- se aplica sobre la parte de la
  cartera que menos se parece a ese supuesto. Y entre carteras hay **10x de dispersion**
  (p10 0%, p90 59%): "la fraccion" es una distribucion, no un numero.
- **La fraccion OBSERVABLE es justo donde el tope NO actua**: los 1.924 SKU muertos salen
  `expired`, sin excepcion. Ademas el relleno de ceros de `_series_from_frame` ya achica
  la media de un muerto 2,6 veces mas que la de un vivo (0,28 contra 0,74), asi que buena
  parte del trabajo ya estaba hecha para las muertes PASADAS. La palanca solo puede pagar
  sobre muertes FUTURAS. Lo deployable es la tasa por ano: **6,8%-12,9% del rango**.

**No se puede deducir la fecha del archivo**, y ese es el resultado que mas pesa: validado
reservando 26 semanas, el falso positivo hace **piso en 10,6%** y no baja ni con medio ano
de silencio sobre seis veces el gap propio del SKU. Uno de cada nueve SKU "obviamente
muerto" vuelve a vender. Es la justificacion de campo de la regla de seguridad que
`src/horizon.py` ya tenia por principio: **el tope encoge, nunca anula**.

Punta a punta por el pipeline real (336 SKU de 60 vendedores): 50,6% trae fecha y solo el
**26,5% de esos** termina topeado -- traer la fecha y que la fecha mueva algo son dos
cosas distintas.

**El defecto que esta medicion encontro, ARREGLADO** (`src/horizon.py::capped_cycle_stock`):
el tope movia `reorder_point`, `order_up_to` y `Q`, y el capital -- `cycle_investment`,
`ss_investment`, `investment` por SKU y el titular `requested_investment` -- se calculaba
sobre la politica SIN topear. El titular salia identico al centavo mientras el deck
anunciaba unidades sacadas del plan y las OPCIONES se describian como la unica opcion que
RESTA capital. Lo encontro correr la capacidad sobre datos REALES; sus tests usan fixtures
sinteticos y no lo veian.

No es una formula nueva: es lo que el repo ya hacia en los otros dos lugares donde una
cantidad se mueve DESPUES de dimensionar -- el redondeo a lote legal (`replace(pol,
order_quantity=Q, expected_cycle_stock=Q/2)`) y la cobertura provisional, cuya rama ya
asignaba `cobertura = tope.trigger` antes de valuar. La rama dimensionada era la unica
que no. El defecto era de ORDEN: `cycle_inv`/`ss_inv` se calculaban ARRIBA del tope.

**Y corrigio un numero publicado.** La primera version del documento decia que el tope
liberaba 12.018 usd (11,2% del titular); eso es la caida del **pico** (el techo de
reposicion x costo). `investment` es `ciclo + buffer`, o sea el **promedio**, y se mueve
**5.103 usd (4,8%)**. El pico es 2,4 veces el titular, y la razon es deliberada:

**EL TOPE NO TOCA EL BUFFER.** Dice "no compres mas de lo que podes vender", no "bajale el
nivel de servicio". El buffer es lo que compro el nivel de servicio DECLARADO y el tope no
renegocia ese nivel: si el buffer solo ya supera el restante, el ciclo se va a cero y ahi
termina. Por eso las dos identidades internas del registro quedan intactas --
`ss_investment == safety_stock x unit_cost` y `reorder_point == mu*L + safety_stock` -- y
`jobs/qa.py::_horizon_issues` ahora las EXIGE (invariantes 5 y 6): un cambio futuro que
encoja el buffer se pone rojo. `tests/test_titular_de_inversion.py` (17) fija las dos
mitades, y el control de siempre sigue: sin columna de fecha el capital sale IDENTICO.

### Una clave de idempotencia constante es un no-op mudo (`tests/test_claves_de_idempotencia.py`)
`nosilo_core.writeback` garantiza, y lo dice en su encabezado, que *"the same
idempotency_key never lands twice"*. Eso es lo que hace seguro reintentar -- pero pide
la contraparte, que es la que se olvida: **la clave tiene que ser DISTINTA para una
operacion distinta**. Reproducido con el conector Odoo de demo, sobre la constante
`"channel-replenish-1"` que traia `channel_replenishment_job`:

    semana 1: stage_restock({SKU-1: +50})   -> applied=True   skip=False
    semana 2: stage_restock({SKU-2: +999})  -> applied=False  skip=True

Contenido distinto (`content_hash` distinto), misma clave, y la segunda se descarta en
silencio **con `idempotent_skip=True`** -- la senal que significa "esto era un
reintento, todo bien". El punto de reorden del segundo SKU nunca aterrizaba.
`repricing_job` tenia el mismo defecto con `f"repricing-{channel}-1"`, constante POR
CANAL, y ahi lo que no aterriza es un precio en un marketplace vivo; mas tres CLI de
`examples/`, que son la plantilla de la que se copia.

No era ignorancia del repo: `excel_replenishment_job` ya derivaba del contenido
estacionado, `shopify_stock_sync` tiene una funcion dedicada, y
`scm_agent/autonomy_promotion.py` lleva el comentario que lo explica entero. La
definicion vive ahora donde vive la semantica:
`nosilo_core.writeback.derive_idempotency_key(prefijo, edits)` -- estable para la misma
operacion (si no, se rompe la idempotencia) y distinta para otra (si no, se rompe la
garantia de que aterrice), con el prefijo separando emisores.

El guard tiene tres mitades: **ninguna clave puede ser un literal** (se decide leyendo
el AST, y reconoce el andamio de `src/connectors/odoo.py`, que pasa un placeholder y
re-keyea con el `content_hash` en la linea siguiente); **los emisores sondeados** se
corren de verdad (misma operacion -> misma clave, operacion distinta -> otra, y las dos
reposiciones distintas aterrizan las dos); y **todo el que estacione un changeset** esta
sondeado o declarado con su razon, incluidos los conectores que solo reenvian.

El otro guard es **estructural y sobre los 60 tools**: recorre por AST toda llamada a
`jobs.*` y se pone rojo si aparece un parametro que el agente no reenvia ni declara por
escrito por que no. Entiende dos cosas o acusa de mas: que un destino se llama desde
VARIOS sitios (alcanza con que uno lo reenvie -- eso daba cuatro falsos positivos) y que
un kwarg puede viajar dentro de un `**{...}` condicional. Las exenciones van por NOMBRE
cuando son genericas (`prepared`, `lang`, `data_source`, `residual`: 65 de las 75 que
quedan) y por `modulo.funcion.parametro` cuando la razon es propia -- `min_periods` esta
ahi porque exponerla dejaria saltear la negativa del motor desde afuera, y
`sop_job.confidence` porque una confianza que el llamador TIPEA no es una medicion.

**Un shock que no puede golpear se RECHAZA**, no se avisa: un `demand_surge` en las
primeras `INITIAL_STOCK_WEEKS` semanas (el mundo dimensiona el stock inicial con esa
demanda y se auto-absorbe) y un shock de suministro que termine dentro de `WARMUP_WEEKS`
(nadie emitio ordenes todavia) salian "absorbido" con costo 0,00 sobre una disrupcion que
nunca ocurrio. Una magnitud `nan`/`inf`, o un spike fraccionario que el reporte publicaria
distinto de lo aplicado, tambien levantan. Y con varios shocks se mide **una** perturbacion
combinada: dos ventanas solapadas no se pueden atribuir por separado.

**Y lo que no se puede rechazar antes de correr se DECLARA despues: `ShockImpact.reached`.**
Rechazar por calentamiento cubre una sola causa de no-op. La general no se sabe hasta
correr -- basta que el SKU apuntado no se pida dentro de la ventana, o que `replan_every`
retrase la primera orden mas alla de `WARMUP_WEEKS` -- y producia el peor renglon posible:
`first_out_of_band_week=None` ya significaba ABSORBIDO, asi que "el carril aguanto" y "la
disrupcion nunca le llego" se leian igual. `score_shock` compara ahora las dos trayectorias
elemento a elemento; si son identicas, `reached=False`, el veredicto queda VACIO
(`recovered` es `None`, nunca `True`) y la fila sale `NO ALCANZADO`. Ese carril tampoco
publica `capture_under_shock` -- seria su captura LIMPIA con otra etiqueta -- y `agregar`
lo cuenta como mundo no medible. No se puede decidir por corrida: medido en la semilla 4,
el mismo shock que no llega al carril de Kern SI lo recibe el piso.

El corte **Anunciado/Silencio** del costo del shock **no es prevision del golpe**:
`Policy.announced` habla de la calidad de lo que Kern LEYO, y la lente le muestra el plazo
PROMETIDO, nunca el real. Medido: con un corte de proveedor y con un surge x3 sobre la
semilla 4, las semanas anunciadas son las mismas que sin shock mientras el costo si se
movio. El numero se publica; el titulo dice lo que es.

### Client parameter profiles (`src/client_profile.py`)
Per-client durable cost/capacity parameters (holding rate, order cost, service
level, lead time, warehouse capacity), keyed by a slugified client name under
`clients/<slug>/profile.json`. The orchestrator merges the profile into the
request's `params` before `tool.prepare` AND `tool.run` (both see the same
merged dict) — profile values only fill gaps, an explicit `overrides`/`params`
value always wins, and profile `lead_time_days` is intake's default lead time
only where the CSV carries none. Pass `Orchestrator.run(..., strict_params=True)`
(CLI: `--strict-params`) to make a tool's `required_client_params` (see
`nosilo_core.registry`) block with `needs_clarification` instead of silently
taking the engine's generic default (0.95 / 0.25 / $75) — the answer, once
supplied, is persisted via `client_profile.upsert_profile(...)` so it is asked
only once per client. Trust boundary: generic labels ("Client", "MCP client")
never resolve a profile; `Orchestrator(clients_root=None)` disables profiles
entirely and is what the webapp/MCP surface uses by default (the `client` field
there is a caller-typed label, not an authenticated identity — opt in locally
via `LINCHPIN_CLIENTS_ROOT`). Not a connector to the client's own system of
record (that's `nosilo_core.writeback`).

  function that uses it, or the app crashes on boot even though the full suite/CI stays
  green (those deps are present transitively in dev). See
  `tests/test_pricing_intel_boot_safety.py` and the `prod-boot` job in
  `.github/workflows/tests.yml`.
- **CI resolves dependencies fresh on every run** — no lock file, no pip cache, so
  an upstream release can turn this repo red with zero commits here. Two habits
  follow. (1) When CI fails on a branch you believe is innocent, **suspect a
  dependency before suspecting your code**: compare the last green run's timestamp
  against the suspect package's PyPI upload dates, and diff the `pip freeze` step
  against the last green run. (2) Don't "fix" this by mass-capping majors — CI
  already runs and passes on pandas 3, numpy 2.5, pytest 9, pyarrow 25, lxml 6 and
  python-stdnum 2 despite floors declared several majors lower, so a blanket cap
  would silently *downgrade* the tested environment. Cap only when a specific
  release actually breaks a specific import, with a comment saying which
  (`mcp>=1.0,<2` is the one live example — mcp 2.0.0 deleted
  `mcp.server.fastmcp`). A nightly cron on `tests.yml` exists so this class of
  breakage surfaces on its own instead of ambushing the next PR or deploy.
- The **books graph** (L3) needs an LLM backend (Kimi/Gemini) to rebuild; the
  **code graph** is AST-only (no key) and the hook handles it.
